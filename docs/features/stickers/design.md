# 闲聊表情包设计

日期：2026-09-09  
状态：已审查，作为本功能的实现依据  
功能说明：[README.md](README.md)  
前置：现有 `MediaRegistry`、`DeliveryPartKind.IMAGE`、运行中心 `/media` 预览、`vision_provider` 配置位。不改变闲聊主链的参与决策。

参考小维的组织方式：短句可以配图、图要有含义、配不上就只发文字。参考 Bot 聊天记录里的任何占比都不是设计依据。

## 审查结论

原稿方向正确，终稿改了五处自相矛盾或容易读错的地方：

1. **「随机」只表示在合适的图里抽一张**，不是再掷一次「这条发不发」。有合适图且过了资格门就配；用冷却避免连发同一张。
2. **GIF 必须人工审核。** GIF 更容易被收入待认知，视觉写完含义后仍停在 candidate；管理员点确认后才可发送。没有自动录取。
3. **状态只保留 `candidate | ready | disabled | rejected`。** 原先的成熟度（unseen / captioned / confirmed）与状态重复，改为由含义来源推导，不当独立状态机。
4. **视觉分两段：先判定是不是表情，再写含义。** 体积/GIF 只做入站粗筛，不能单独决定可发送。
5. **偷来的图就是 Bot 自己的图鉴。** 来源群只作审计记录，不限制发送；ready 之后各群都可以配。

业界对照（MaiBot、stealer、smart_imagechat）只用来补运营缺口：库上限、拒绝集、哈希唯一、待认知与可用库分开。不把它们的发送比例抄过来。

## 1. 目标

成品是**表情图鉴**，不是搜图插件。每张图四件事：预览、含义、何时用/不用、从哪来以及能不能发。

闲聊有两种发图，都只发图鉴里已经 ready 的图：

- **配图（伴奏）**：先写出并校验回复，再按自己这句话抽一张。抽不中只发文字，不解释。
- **要图（主菜）**：群友在向 Bot 要表情。先写一句很短的接话，再按**群友这句话**抽图。只要一张：先发接话，再另发一张图。要很多张：先发接话，再发一条合并转发，一次最多 15 张。发不出图时仍要回话：用当前人格现写一句，说明这回给不了。禁止固定台词，禁止沉默，禁止说库存、路径、开关名。

### 1.1 认知卡

查询不走模型：

```text
预览：缩略图
含义：摊手无奈，带一点「我也没办法」
适用：拒绝、解释做不到、被追问后收束
禁用：危险、认真技术帮助、知识纠错
态度：无奈（可多值）
强度：低
关系：陌生人可用
来源：群内捕获 | 管理员导入
状态：candidate | ready | disabled | rejected
```

含义必须通过交换测试：把图换成另一张，这句话应明显不成立。通不过或为空时写「认知尚未形成」，禁止「可爱 / 有趣 / 表情包」。未形成认知的图不得发送。

### 1.2 表情复读不在这里做

群友连续发同一张自定义表情、Bot 原样跟一张，这是**表情包复读**，要做，但属于现有闲聊复读链路（`ChorusDetector` → `JOIN_CHORUS`），不是本功能。

现在文字复读和表情包复读都走这条链路。表情包用同一文件哈希当成「相同内容」，发出去是现场那张图。照片、截图、QQ 商城表情、系统黄豆不成链。规则仍是两人以上、不是单人刷屏、针对自己不跟着念、每链一次、不安全就沉默。跟的是现场那张图，不走图鉴认知，也不从图鉴里另挑一张。

本功能只做图鉴、成文后配图、群友要图、捕获。文字复读时本功能仍然不配图（资格门排除 `JOIN_CHORUS`）。要图不是复读：对方要的是 Bot 自己库里的一张，不是把现场那张再跟一遍。

### 1.3 不做

- `bq`、表情制作、联网搜包
- 发送时现编含义，或让模型在候选里点选并解释
- 硬分类文件夹当主界面
- 捕获或发送 QQ 商城表情、系统黄豆
- 把选图失败交给语言模型
- 把参考 Bot 的样本占比写成阈值
- 在本功能里做斗图接龙、图片团战，或另起一套表情复读
- 库满自动删除旧图
- 热路径加向量库或二次聊天模型调用
- 浏览器暴露原始媒体 URL、QQ 号、磁盘路径

## 2. 对象

五种核心对象。视觉模型不得进入这些契约。

| 对象 | 职责 |
|---|---|
| `StickerAsset` | 文件、哈希、MIME、来源、启用 |
| `StickerCognition` | 含义、适用/禁用、态度面、强度、关系门槛、含义来源 |
| `CaptureCandidate` | 尚未可发送的捕获；含判定结果 |
| `AccompanimentDecision` | 本轮是否配图、选中哪张、或为什么不配 |
| `DeliveryBundle` | 已有；本功能至多追加一个 IMAGE part |

身份键是文件内容 SHA-256，不是消息 ID、文件名或平台 URL。

许可证：管理员导入仍用 `owned / licensed / public_domain / cc0 / cc_by`。群内捕获用 `group_captured`，不伪装成知识共享协议。

## 3. 链路

```text
成员发出自定义图
  → 入站门（类型、MIME、大小、拒绝集、像表情粗筛、非自己）
  → 哈希已存在：只记再见，不新建、不重跑视觉
  → 哈希不存在：写入 candidate（不可发送）
             ↓
     后台：判定是不是表情 → 通过则写含义
     或管理员手写含义
             ↓
     管理员确认 → ready
             ↓
闲聊生成并校验正文
  → 资格门（动作、安全、冷却、库非空）
  → 用正文和态度检索 ready 图
  → 合格集合内随机一张
  → TEXT + 至多一张 IMAGE
  → 空集或未过门：只发 TEXT
```

没有视觉模型时：捕获仍入库为 candidate，页面显示「认知尚未形成」，只能手写含义后发送。

## 4. 认知

### 4.1 字段

- `meaning`：≤ 48 字；空则不可发送
- `use_when`：≤ 3 条
- `do_not_use`：≤ 3 条
- `attitudes`：有界多值，仅检索。`amused` `tease` `helpless` `confused` `startle` `wronged` `refuse` `agree` `acknowledge` `warm` `close` `proud`。与好感门槛无关。
- `intensity`：0–100
- `min_familiarity`：好感度下限，对应公开关系阶段（谁都行 / 认识 / 熟悉 / 亲近 / 默契）。看这张图发给不够熟的人会不会别扭，不跟口气挂钩。
- `max_boundary_pressure`：关系门槛
- `caption_source`：`admin` | `vision` | `mixed`

### 4.2 视觉任务

后台、单飞、有界队列。失败停在 candidate。

1. **判定**：表情/梗图，还是照片、截图、证件、长文？不是表情 → `rejected`，哈希进入拒绝集，永不 ready。
2. **认知**：仅对判定通过的图填写 4.1。先看画面，再用当前人格口吻写成她会发出去的那句话；能结合网络梗就结合，软萌卖萌按动作写、不要硬套。适用/禁用、口气、好感门槛一并填。视觉只注入公开的自称、语气和说话习惯，不注入私有 canon。动图先合成可见帧，再均匀抽 4–6 帧横拼成一张静图送给视觉模型；拼失败才退回第一帧。管理页预览和群里发出去仍是原 GIF。禁止外貌、年龄、真实身份、OCR 长文、文件名猜测。过滤 URL、长数字、本地路径。整句只写「可爱」仍不可发送。

产品层不建文件夹。态度、状态、来源只做过滤面。管理员先有图和含义。

## 5. 配图

### 5.1 资格门

全部成立才检索：

- 已有通过审核的正文
- 动作不是沉默、原文复读、安全最低帮助
- 不是知识纠错或高风险能力结果
- 本轮允许媒体（闲聊允许；安全/聚焦任务不允许）
- 存在至少一张 ready 且认知完整的图

文字够不够不再禁止配图。配图是伴奏，不是文字不够时的替代。

### 5.2 检索与随机

输入：校验后的回复文本 + 本轮态度/动作。

1. 排除 disabled、冷却中、关系不合、禁场景命中的图
2. 剩余图按含义句与正文的词面重叠打分，态度相容加分
3. 低于阈值视为不适合
4. **在合格集合里按权重随机抽一张**（不是永远最高分）。刚用过的降权
5. 空集 → 只发文字，群友看不见这次失败

「随机」到此为止。不在「已经合适」之后再掷一次发不发。

首版不做发送时的向量检索，也不再调一次模型点选。词面会漏「字面不同、语气相近」的图：靠改含义补，不靠热路径加模型。

### 5.3 发送

- 一条逻辑回复：配图仍是 1–2 段文字，至多 1 张图，图和文字同一条消息
- 要图只要一张时：先发短接话，再另发一张图，两条消息
- 要图要很多张时：先发短接话，再发一条合并转发；转发里每张图一个节点，最多 15 个，不在群里连刷多条
- 图必须是 registry 再验证后的本地文件
- 影子模式只记录「本来会配哪张 / 哪一包」，不发给群
- 配图与偷取两个独立开关。关掉配图 = 闲聊不再自动配图，不是关掉要图的回话

### 5.4 群友要图

和配图共用图鉴、冷却、好感门槛。配图跟文字同一条发出；要图先回话，再另发图。差别在检索输入、这张图是不是这轮的主菜，以及发不出图时仍必须回话。

成立才走要图，否则仍是普通配图：

- 闲聊，且话是对 Bot 说的（点名、回复、明显在问 Bot）
- 对方在要一张表情，不是要照片、截图、商城表情、系统黄豆，也不是 `bq` 指令
- 动作不是沉默、复读、安全最低帮助、知识纠错。硬边界仍可要图发图；配图不发

检索与发送：

1. 查询句是**群友这句话**（他们要什么），不是 Bot 刚写的接话
2. 对方只要一张，或没说要多少：在合格集合里随机 **1** 张，先发短接话，再另发这张图
3. 对方明显要很多张（一堆、几张、多来点、打包）：在合格集合里随机最多 **15** 张，**同一哈希不重复**，先回话再用已有 `FORWARD` 合并转发一次发出；合格图不够 15 就有多少给多少，不凑数、不解释上限
4. 没指明要哪种时，合格集合 = 过了好感门槛和冷却的 ready 图；听出种类了再按含义 / 适用 / 口气词面重叠过滤。触发是自然语言，不靠固定句式；唤醒词和客套不算种类，「来个无奈的」这种没说「表情」也算要图
5. 好感门槛仍看对方公开好感，与口气勾选无关
6. 关掉配图只禁止闲聊伴奏。要图只要库里有可发的图、本轮不是安全/聚焦禁媒体，就仍发图；连着要被判成硬边界或只许发文字时，要图仍发
7. 发不出图（库空、对不上、关系不够、不安全、本轮禁媒体）→ **仍生成回复**，告诉对方这回给不了。句子由当前人格按现场现写，不设固定台词，不解释库存、路径、开关
8. 热路径仍不调视觉、不让模型在候选里点选

发出去的图都记使用。连着「再来一堆」是新的一轮，刚用过的照常降权。不要把 15 张拆成 15 条群消息。不安全或越界的要图走拒绝口吻，不发图，但仍说话。

## 6. 捕获

### 6.1 入站（新建卡）

全部成立才新建：

- 片段是 `image`（不是 `mface`、`face`、视频、文件、转发）
- MIME 为 png/jpeg/gif/webp，体积在上限内
- 哈希不在图鉴、也不在拒绝集
- 粗筛更像表情：优先动图；过宽过大的 JPEG 静图跳过
- 发送者不是 Bot 自己

### 6.2 再见同一张

| 已有状态 | 再发同一哈希 | 视觉 |
|---|---|---|
| ready | 再见次数 +1，不改第一来源和含义 | 否 |
| candidate（进行中） | 挂到已有卡 | 否，不重复排队 |
| candidate（失败或空含义） | 同上 | 否；管理页「重新认知」才再跑 |
| disabled | 同上，不自动启用 | 否 |
| rejected | 直接跳过 | 否 |
| 手写过含义 | 不覆盖 | 否 |

哈希列唯一约束。并发两个「第一次见到」时，后到者按已存在处理。看起来一样但字节不同（重压缩）视为另一张，本阶段不做感知哈希；重复由管理员停用其一。

重新认知的唯一入口是管理页。热路径永不重跑。

### 6.3 录取

判定通过且含义非空的图仍停在 candidate，**管理员确认后才 ready**。GIF 与静图同样须人工确认，视觉路径永不自动录取。

### 6.4 来源记录与容量

- 捕获图记下来源群、来源事件，便于审计；**不限制发送群**
- 待认知上限 30；满则停建新卡，只对已有哈希记再见
- 正式库（ready+disabled）上限 200；满则停止自动捕获，不删旧图
- 打开收表情后，已启用 Groupmate 的群都会捕获；关掉则各群都不收新图
- 页面必须显示池满/库满，不能静默丢已有卡

## 7. 管理页

工作区 `#/stickers`。

1. **待认知**：candidate、视觉失败、含义为空
2. **图鉴**：ready/disabled 网格；卡上直接是含义句
3. **详情**：认知全文、适用/禁用、态度、关系、使用次数、来源（仅记录）、改写、停用、删除、重新认知

动作：手写含义、启用/停用、上传、确认、驳回（进拒绝集）、删除、重新认知。无普通群员编辑，无公开 URL 导出。不提供「移动到某分类」。

## 8. 与现有代码

复用：`MediaRegistry` 落盘与校验、`DeliveryPartKind.IMAGE`、`message_media` 与 `/media`、知识库那种待确认工作流、`vision_provider`。

改写：`MediaAsset` 增加认知与 `group_captured`；选图改为成文后检索 + 随机，取消「文字足够就不配图」；闲聊允许注册媒体，安全/聚焦仍只发文字；`ReplyExecutor` 在校验正文后，配图把图挂在文字同一条，要图则先入队文字再另入队 IMAGE 或 FORWARD。群友要图时按自然语言听要不要图、要哪种；一张先回话再发图，很多张用已有 `FORWARD` 合并转发一次最多 15 张。

不接入 AstrBot meme 插件，也不在成文前用旧的 `MediaIntent` 选图。

## 9. 实施顺序

1. 图鉴契约：卡、状态、哈希唯一、磁盘校验。此时还不能发、不能偷。
2. 管理页：网格、待认知、手传、手写含义。
3. 成文后配图：资格门、检索、随机、IMAGE。无图时与现在相同。
4. 群内捕获：入站、再见、两段视觉、容量。GIF 须人工确认。
5. 群友要图：对 Bot 要表情时按对方这句话检索；未指明则在合格图里随机。无图时只回短接话。

没有认知卡之前不要接通发送。没有管理页之前不要自动捕获。没有资格门之前不要随机配图。没有配图链路之前不要接通要图。

## 10. 怎样算做对

- 管理员能看见每一张图，以及 Bot 对它的含义
- candidate / 空含义 / rejected 从未真实发出
- 同一句在合格图多于一张时，多次可以抽到不同张，且不会抽到禁场景的图
- 自定义图进入待认知；明显像照片的 JPEG 默认不进
- 同一哈希再见不新建、不重跑视觉
- 并发首次见到只产生一张卡、一个视觉任务
- 驳回哈希不再进待认知
- 捕获图一旦 ready，各群闲聊都可以配；来源群只作记录
- 池满、库满时停收，不删旧图
- 没配上时群友只看到原来的文字
- 对 Bot 说「来张表情」会从图鉴给一张；说「发个无奈的」按这句话检索，不是按 Bot 的接话
- 要很多张时走合并转发，一次最多 15 张，不连刷；不够 15 有多少给多少
- 要图对不上或发不出图时仍回话，句子现写，不说库存、不用固定台词
- 发送路径不新增一次视觉或聊天模型调用
