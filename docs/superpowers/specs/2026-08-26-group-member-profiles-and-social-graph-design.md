# Groupmate 群成员画像与社交关系图设计

日期：2026-08-26  
状态：已确认，待实施  
范围：Groupmate 核心闲聊链路中的持续成员认知、群友关系网络、画像检索与管理能力

## 1. 背景

Groupmate 作为 AstrBot 插件运行在 NapCat → AstrBot → Groupmate 的消息链路中。插件的核心价值不是堆叠外部命令，而是让 Bot 在群聊中更自然地观察、理解、参与和表达。

现有系统已经具有：

- 参与判断和 SHADOW 观察链路；
- 群聊场景理解；
- Bot 与成员之间的关系投影、好感度和关系记忆；
- 成员昵称、头像等展示目录；
- 直接模型认知通道和失败降级；
- 运行中心与消息处理链路展示。

但这些能力仍缺少“对每位群友长期、独立、可修正的认知”。当前记忆主要围绕当前发言者和 Bot—成员关系，无法稳定表达：

- 这个人是谁、如何称呼；
- 他喜欢或讨厌什么；
- 他说话和做事有什么独特模式；
- Bot 和他经历过哪些重要事件；
- 他与其他群友之间是什么关系；
- 这些认知如何随时间变化并影响回复。

本设计新增“群成员画像系统”。它不是一次性摘要，也不是简单标签库，而是一套证据优先、持续演化、按需检索的群体认知基础设施。

## 2. 产品目标

### 2.1 核心目标

Bot 会持续积累对每位群友的了解，包括群友信息、喜恶、边界、行为风格、代表经历和群内关系，并让这些认知自然影响后续判断与表达。

### 2.2 用户可感知结果

经过一段时间的群聊后，Bot 应能做到：

1. 识别昵称变化和历史别称，不把昵称当成唯一身份；
2. 对不同成员采用有差异、但不刻意复述标签的表达方式；
3. 记得有代表性的善意、冲突、承诺和共同经历；
4. 理解成员之间的稳定互动关系，减少错误指代和不合时宜的插话；
5. 面对他人编造的成员信息时保持怀疑，不把单次第三方说法当事实；
6. 允许成员查询和纠正自己的画像；
7. 在模型不可用时继续接收消息、执行规则判断和读取已有画像。

### 2.3 非目标

本轮不做：

- 根据群聊自动创作成员长篇传记或虚构世界观；
- 推断外貌、年龄、恋爱、家庭、疾病、政治等敏感信息；
- 用好感度代替权限系统；
- 将一个群的私人画像默认带入另一个群；
- 每条消息同步调用画像模型并阻塞回复；
- 为了“个性化”而在每句话里重复角色设定或成员标签。

## 3. 设计原则

### 3.1 四域分离

系统必须保持四个领域独立：

1. **成员身份**：这个人是谁；
2. **成员画像**：Bot 对这个人的认知；
3. **社交关系**：成员与成员之间的关系；
4. **Bot 关系**：Bot 与成员之间的好感度、关系阶段和共同经历。

权限系统继续独立。开发者、管理员等身份只影响授权和稳定身份认知，不被好感度或社交关系覆盖。

### 3.2 证据优先

模型只能提出候选认知，不能直接写入正式画像。所有画像事实、关系和代表经历都必须关联来源事件、说话者、时间和可信度。

### 3.3 策略优先、模型增强

账号 ID、昵称、群角色、@、回复关系和活跃度由本地规则确定。模型只处理规则难以可靠完成的语义提取，例如偏好、边界、行为风格、重要经历和关系候选。

### 3.4 后台演化，不阻塞消息

画像提取、合并和快照生成位于后台任务，不进入消息回复关键路径。消息先可靠落库；模型失败时保留待处理任务并降级，不影响群聊主链路。

### 3.5 相关才使用

回复时不注入完整画像，只检索当前发言者、被提及成员、当前话题和必要关系对应的少量信息。

### 3.6 可修正、可过时、可追溯

认知不是永久真理。事实可以待确认、被纠正、过时、失效或被新事实取代；管理员能够追溯来源并审计变化。

## 4. 总体架构

```text
NapCat 群消息
    ↓
AstrBot 事件与消息组件
    ↓
Groupmate Bridge
    ├─ 前置命令 / 外部插件所有权判断
    ├─ 身份解析与消息标准化
    └─ 原始观察事件落库
             ↓
    ┌────────┴────────┐
    │                 │
确定性本地规则       后台画像认知任务
身份、别称、@、回复   偏好、边界、风格、经历、关系候选
    │                 │
    └────────┬────────┘
             ↓
      本地证据与策略校验
             ↓
    ┌────────┼──────────┐
    │        │          │
画像事实   代表经历   社交关系边
    └────────┼──────────┘
             ↓
       成员画像快照生成
             ↓
    ┌────────┴────────┐
    │                 │
参与判断检索         回复生成检索
```

新增能力应位于独立的 `groupmate/social_runtime/profile/` 领域，不把画像逻辑堆入 AstrBot Bridge、参与策略或现有好感度投影器。

## 5. 领域模型

### 5.1 MemberIdentity：稳定成员身份

建议主键：

```text
(persona_id, platform, actor_id)
```

字段包括：

- `persona_id`：当前 Bot 人格；
- `platform`：适配平台，例如 QQ；
- `actor_id`：NapCat/AstrBot 传入的稳定账号 ID；
- `current_display_name`；
- `current_avatar_url`；
- `system_roles`：群主、管理员、Bot 开发者等确定性身份；
- `first_seen_at`、`last_seen_at`；
- `created_at`、`updated_at`。

### 5.2 MemberAlias：昵称与别称历史

字段包括：

- `identity_id`；
- `group_id`；
- `alias`；
- `alias_type`：平台昵称、群名片、自称、群内别称、人工确认；
- `confidence`；
- `first_seen_at`、`last_seen_at`；
- `source_event_id`；
- `status`。

昵称只用于解析和展示，绝不作为成员唯一主键。别称相似不能自动合并身份。

### 5.3 ProfileFact：原子画像事实

一条事实只表达一个可验证认知，例如：

- 喜欢冷饮；
- 不喜欢含糊解释；
- 常用短句推进讨论；
- 擅长插件开发；
- 明确不接受某类玩笑。

字段包括：

- `fact_id`；
- `persona_id`、`group_id`、`subject_id`；
- `category`：identity、preference、dislike、boundary、interest、skill、speech_style、behavior_pattern、group_role；
- `value_json`；
- `summary`；
- `source_kind`：system、self_statement、observed_pattern、third_party_claim、admin_correction；
- `source_actor_id`、`source_event_id`；
- `confidence`；
- `evidence_count`；
- `status`：proposed、confirmed、disputed、stale、superseded、rejected；
- `valid_from`、`valid_until`；
- `supersedes_fact_id`；
- `injectable`；
- `created_at`、`updated_at`。

### 5.4 EpisodeEvidence：代表经历

代表经历用于保存能形成长期关系意义的具体事件，而不是逐条聊天流水账。

字段包括：

- `episode_id`；
- `persona_id`、`group_id`；
- `title`、`summary`；
- `participants`；
- `event_ids`；
- `episode_type`：help、promise、conflict、repair、shared_achievement、boundary_violation、other；
- `valence`、`importance`；
- `confidence`；
- `status`；
- `occurred_at`、`last_reinforced_at`；
- `created_at`、`updated_at`。

Bot 可以记得具体的好与坏，但不能仅凭一次误解永久定性。负面事件允许随道歉、修复和时间发生状态变化。

### 5.5 SocialEdge：群友关系边

关系边表达成员之间有证据的互动模式：

```text
成员 A → 关系类型 → 成员 B
```

字段包括：

- `edge_id`；
- `persona_id`、`group_id`；
- `source_member_id`、`target_member_id`；
- `relation_type`：frequent_interaction、familiar、supportive、technical_peer、teasing、conflict、avoidance、custom；
- `direction`：directed、bidirectional；
- `strength`、`confidence`；
- `evidence_event_ids`；
- `status`；
- `valid_from`、`valid_until`；
- `last_observed_at`；
- `created_at`、`updated_at`。

敏感关系不在允许自动推断的枚举中。群友的单次陈述只能产生低可信候选边。

### 5.6 ProfileSnapshot：紧凑画像快照

快照是展示和模型注入层，不是真相源。字段包括：

- `member_id`、`group_id`；
- `one_line_portrait`；
- `group_roles`；
- `individual_fingerprints`；
- `preferences_and_boundaries`；
- `representative_episode_ids`；
- `relationship_summary`；
- `maturity`：new、forming、stable；
- `source_revision`；
- `generated_at`。

快照可以重新生成；原子事实、经历和证据才是可审计事实源。

### 5.7 GroupPortrait：群体画像

群体画像描述群整体，而不是成员隐私的简单拼接：

- 常见话题与群文化；
- 活跃时间和对话节奏；
- 常见内部称呼；
- 主要群内角色构成；
- 互动规范和明显边界；
- 当前阶段性事件；
- 关系网络的聚合结构。

群体画像同样只保存有证据、可过时的信息。

## 6. 信息获取与可信度

### 6.1 确定性信号

无需模型即可确认：

- 平台账号 ID；
- 当前昵称、群名片、头像；
- 群主、管理员等平台角色；
- @、回复、引用对象；
- 消息时间和活跃度；
- 用户显式执行的画像纠正命令。

### 6.2 语义信号

模型只产生结构化候选：

- 本人明确表达的喜恶和边界；
- 多次观察到的表达与行为模式；
- 有代表性的群聊事件；
- 群内角色候选；
- 成员关系候选；
- 对旧事实的纠正、冲突或失效信号。

### 6.3 来源权重

从高到低：

1. 系统确定事实和管理员人工纠正；
2. 当事人对自己的明确陈述；
3. 多次独立行为观察；
4. 模型对长期模式的概括；
5. 第三方陈述；
6. 单次玩笑、反讽或无法确认的转述。

第三方单次陈述只能进入 `proposed` 或 `disputed`，不得直接进入可注入画像。

### 6.4 冲突与时间

- 新事实与旧事实冲突时，不直接覆盖；
- 保留双方证据并比较来源、时间和重复次数；
- 明确自我纠正可以使旧事实 `superseded`；
- 习惯、兴趣等时间敏感事实会随长期缺乏证据逐渐 `stale`；
- 稳定身份、明确边界不会仅因时间自动消失；
- 管理员和当事人纠错必须立即阻止错误事实继续注入。

## 7. 后台认知任务

### 7.1 调度

画像认知不对每条消息同步调用模型。建议按以下任一条件触发批次：

- 累计 20 条符合条件的新群聊消息；
- 距上次处理达到 10 分钟；
- 管理员主动要求刷新成员画像。

单批限制消息数和输入大小，按成员与对话上下文分组。

### 7.2 模型调用

- 使用插件自己的直接模型通道；
- 单独的 `profile_extractor` 任务类型；
- 输出必须通过本地 JSON Schema 校验；
- 模型不能直接写数据库；
- 后台任务允许比实时参与判断更长的超时，但不占用实时认知截止时间；
- 超时、限流、无效输出进入可重试队列；
- 原始 Provider 异常不写入用户可见画像。

### 7.3 快照刷新

发生以下情况时刷新成员快照：

- 有新事实被确认；
- 重要经历建立或状态改变；
- 关系边显著变化；
- 用户或管理员纠正画像；
- 快照超过刷新周期且有新证据。

没有变化时不反复调用模型重写画像。

## 8. 个体化质量控制

### 8.1 交换测试

将两名成员名字互换后，如果画像仍然成立，说明画像过于通用，不应进入稳定快照。

### 8.2 证据测试

每个抽象判断必须至少关联一条具体证据；稳定行为风格通常要求多次观察。

### 8.3 行为价值测试

只有能够实际改变称呼、解释深度、玩笑尺度、话题选择、参与时机或态度的认知，才进入可注入画像。

### 8.4 叙事边界

参考目标 Bot 和《星星花纪年》的个体化组织方式，但只采用：

1. 一句话鲜明画像；
2. 群内角色；
3. 个体指纹；
4. 少量代表经历；
5. 关系与变化。

不虚构年龄、外貌、身份背景、世界观或长篇人生故事。

## 9. 与现有好感度系统的关系

现有 `RelationshipProjection` 继续负责 Bot—成员关系变化，好感度不并入成员画像事实表。

画像系统为关系投影提供：

- 已确认的偏好与边界；
- 有代表性的正负事件；
- 最近关系变化的可解释证据；
- 与成员交流时的个体化线索。

好感度反过来只影响情绪距离和表达尺度，不篡改画像事实。

开发者特殊性设计为：

- `system_roles` 中的稳定开发者身份；
- Bot 关系中的特殊起点和称呼；
- 仍会因实际互动积累正负关系；
- 不具有永久满好感或负面事件豁免。

## 10. 与参与判断和回复的集成

### 10.1 参与判断

画像只提供辅助信号：

- 是否正在延续与 Bot 的对话；
- 该成员是否习惯用某个已确认别称呼唤 Bot；
- 当前成员之间是否存在自然对话关系；
- Bot 插话是否可能打断对话。

显式 @Bot、回复 Bot、确定性别称呼唤仍由本地高优先级规则处理，不能依赖画像模型。

### 10.2 回复检索

每次回复最多检索：

- 当前发言者的一份紧凑画像；
- 最多两名被明确提及或与当前话题强相关的成员；
- 最多三条相关事实；
- 最多两条代表经历；
- 必要的社交关系边；
- 当前 Bot—成员关系摘要。

检索结果受独立字符或 Token 预算约束。完整画像和完整关系图不得进入普通回复提示词。

### 10.3 表达原则

画像影响：

- 称呼；
- 直接或委婉程度；
- 玩笑和吐槽尺度；
- 解释深度；
- 对过去事件的自然引用；
- 亲近、克制、不满或记仇的情绪。

画像不得导致 Bot 机械复述“你是某种人”，也不得句句提及角色元素。

## 11. 隐私、权限和跨群边界

### 11.1 可见性

- 普通成员只能查询自己的完整画像；
- 管理员可以在后台查看、纠正和审计群成员画像；
- 其他成员不能通过普通命令查看某人的完整画像；
- 公开的好感度榜单与私有成员画像继续分开。

### 11.2 跨群策略

- 稳定平台身份和明确开发者身份可以跨群识别；
- 昵称历史按群保存，也可关联到同一稳定身份；
- 画像事实、代表经历、社交关系和好感度默认按群隔离；
- 不自动把某群的私事带入另一个群；
- 未来若支持跨群记忆，必须显式配置并增加可见性策略。

### 11.3 删除与纠正

成员可以请求：

- 查看自己的画像；
- 纠正自己的某条事实；
- 删除不希望继续使用的画像事实；
- 停止画像个性化注入。

管理员可以执行身份拆分、身份合并、证据失效和关系纠正。所有操作进入审计日志。

## 12. 命令与界面

### 12.1 群聊命令

建议支持：

- `查看我的画像`
- `我的画像`
- `纠正画像 <内容>`
- `删除画像 <编号>`

命令由 Groupmate 确定性识别并直接查询本地数据，不调用模型。命令被插件接管后停止向 AstrBot 默认回复链路继续传播，避免重复回复。

### 12.2 管理页面

新增“群成员画像”页面，信息层级为：

1. 成员列表：头像、昵称、画像成熟度、最近变化；
2. 成员详情首屏：一句话画像、群内角色、个体指纹；
3. 喜恶与边界；
4. Bot—成员关系和好感度摘要；
5. 代表经历时间线；
6. 群友关系网络；
7. 最近认知变化；
8. 证据与审计折叠区；
9. 纠正、失效、合并身份操作。

画像首页突出“这个人是谁”，不先展示模型耗时、输入大小等技术诊断。运行中心仅显示画像任务是否正常、积压量和最近更新时间，详细技术数据进入折叠审计区。

### 12.3 群体画像页

群体画像展示：

- 群的一句话定位；
- 常见话题与活跃节奏；
- 群内角色构成；
- 成员画像入口；
- 可交互关系网络；
- 最近群体变化和阶段性事件。

关系图必须同时提供文字关系列表，不能只依赖难以阅读的节点连线。

## 13. 数据保留与压缩

- 最近原始消息作为热证据保留，周期可配置；
- 过期普通消息可以在形成事实或经历后压缩；
- 高重要度代表经历及其关键证据长期保留；
- 被纠正事实保留审计记录，但不再注入；
- 画像快照可随时从当前有效事实重新生成；
- 清理策略不得造成画像和证据引用悬空。

默认建议：近期原始证据保留 30 天，代表经历和已确认事实按状态长期保存。部署者可根据群规模调整。

## 14. 降级与故障隔离

### 14.1 模型不可用

- 消息仍写入原始事件；
- 确定性身份和互动信号继续更新；
- 画像提取任务进入重试队列；
- 使用最后一个有效画像快照；
- 不向群内发送“暂时无法可靠回答”之类无关错误回复。

### 14.2 模型输出不可用

- Schema 不通过则整批候选不落正式表；
- 不暴露模型原始输出；
- 记录安全诊断码；
- 达到重试上限后等待下一批证据重新评估。

### 14.3 数据不充分

- 展示“正在形成画像”，而不是生成泛化套话；
- 不足以确认的内容停留在候选层；
- 回复继续使用普通人格和当前上下文。

## 15. 验收标准

### 15.1 身份

- 同一账号修改昵称后仍为同一画像；
- `玲151` 和 `小赛151` 不会因名称相似被合并；
- @、回复和引用对象能够准确映射到成员身份；
- 平台群角色和开发者身份来自确定性配置或系统数据。

### 15.2 事实与证据

- 用户自述可以形成高可信候选；
- 单次第三方说法不会成为正式事实；
- 多次行为观察可以逐步形成稳定风格；
- 新信息能够使旧信息过时或被取代；
- 用户纠正后，错误事实立即停止注入。

### 15.3 社交关系

- 多次可观察互动可以形成有证据的关系边；
- 单次玩笑不能形成高可信敏感关系；
- 关系变化具有时间和证据记录；
- 关系检索能改善指代、对话归属和插话判断。

### 15.4 运行链路

- 后台画像模型超时不阻塞消息处理；
- 模型不可用时本地规则和已有画像仍可用；
- 查询画像不需要调用模型；
- 前置命令只产生一次回复，不与 AstrBot 默认链路重复；
- 回复只注入相关画像并满足预算限制。

### 15.5 个体化

- 两名成员画像交换名字后不能同样成立；
- 每个稳定抽象判断都有可审计证据；
- 画像能够实际改变回复策略；
- 数据不足时不会伪造个性；
- Bot 不会机械复述画像或角色设定。

### 15.6 隐私

- 普通成员不能查看他人完整画像；
- 跨群画像和关系默认隔离；
- 删除、纠正和停用个性化可以生效；
- 权限不受好感度或社交关系影响。

## 16. 实施边界与顺序

本轮作为一项完整正式能力交付，内部按以下顺序实施：

1. 身份、别称和数据库迁移；
2. 画像事实、证据和后台提取任务；
3. 快照生成和个体化质量校验；
4. 成员—成员社交关系图；
5. 回复与参与判断的预算化检索；
6. `查看我的画像`、纠错和停止注入命令；
7. 管理页面和群体画像展示；
8. 定向场景测试、故障降级测试和安装包验证。

实施时只运行与变更直接相关的定向测试，不进行无意义的大范围重复测试。

## 17. 参考依据

- MaiBot A_Memorix：在规划前按相关性注入少量成员画像，并从事实与近期证据更新画像；
- Zep/Graphiti：将 episode、entity、fact、relationship、summary 分层，并保留时间有效性和冲突关系；
- Mem0 Graph Memory：用实体与关系表达社交记忆，而非只保存文本摘要；
- Generative Agents：观察、记忆、反思和检索共同形成连续行为；
- NIST RBAC：权限与社交关系、好感度保持分离；
- 目标群聊数据：验证了别称解析、第三方成员认知、习惯记忆、立场保持和边界记忆的重要性；
- 《星星花纪年：小饼干回收部奇谭》：仅借鉴一句话人物定位、代表经历、群内角色和关系变化的组织方式。

## 18. 最终定义

> Groupmate 会长期、独立地认识每一位群友，记住其信息、喜恶、边界、行为方式、代表经历和群内关系；这些认知有证据、可纠正、会过时，并只在相关时自然影响 Bot 的参与判断与表达。
