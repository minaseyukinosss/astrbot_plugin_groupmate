# 新库画像成长链路加固设计

## 目标

在下一版本使用全新数据库启动的前提下，保证群成员画像能够跨后台批次积累、整群画像能够自动刷新，并且画像后台故障、命令噪声和管理页枚举都可被准确观察和控制。

## 发布前提

线上旧数据库不迁移、不重放。正式切换时先停止 AstrBot，保存一致性备份，再移走主数据库及 `-wal`、`-shm` 文件，让新版本创建全新数据库。代码不得主动删除任何数据库文件。

## 跨批证据累计

模型事实使用稳定 claim ID：

```text
persona_id × group_id × subject_id × category × source_kind × normalized_summary
```

规范化摘要使用 NFKC、统一空白、英文小写并忽略常见中英文标点。`source_kind` 必须参与 ID，确保第三方说法不会与本人自述合并。

同一 claim 再次出现时，合并唯一证据 ID、保留最高置信度和最早生效时间，再交给本地证据策略重新判定。`observed_pattern` 累计到三条不同证据且置信度达到 0.88 后确认。已经确认的事实不会被较弱的新候选降级。

成员关系继续使用双方、关系类型和方向组成的稳定 edge ID。不同批次的相同 edge 合并证据、强度和置信度，累计三条不同直接互动证据后确认。提示词允许模型输出证据不足的关系候选，本地规则负责保持其不可注入。

共同经历暂不跨批做语义合并，避免名称相近但实际不同的事件被误合并。

## 整群画像刷新

每个群完成画像批次后，后台服务都重建该群的安全汇总。输入仅包含：

- 当前群的成员快照；
- 已确认、未过期的成员关系；
- 画像观察消息的活跃小时分布；
- 成员快照中已公开用于群内画像的角色统计。

本阶段不把个人偏好或边界汇总成公共话题。没有已确认群文化时，摘要使用不泄露个人事实的确定性文案，例如“已形成 3 位成员画像，群体认知持续更新”。

## 后台健康状态

`ProfileService` 维护内存健康快照：任务是否运行、各群待处理数量、最后尝试时间、最后成功时间和最近安全诊断码。模型返回合法空数组也算成功，但诊断显示 `profile_no_candidates`，从而与真正产出候选区分。

后台循环捕获未预期异常，记录 `profile_worker_failed` 并继续下一轮，不允许一次异常永久杀死画像任务。模型网络类错误继续沿用现有重试策略。

Bridge 将画像健康快照加入实时运行状态；控制面 `health` 接口透传；群成员画像页面以简短状态条展示，不公开原始模型输出或异常字符串。

## 命令噪声过滤

画像观察入口在入队前检查已经解析出的互动归属。以下消息不进入画像队列：

- `social_eligible` 为 false；
- `interaction_owner` 为 `EXTERNAL_PLUGIN`；
- 唯一成员画像命令 `查看我的画像`。

普通群聊、未直接呼叫爱弥斯的消息仍正常进入画像队列。

## 管理页面枚举

前端成熟度映射使用后端真实值 `new / forming / stable`。关系映射完整覆盖 `frequent_interaction`、`familiar`、`supportive`、`technical_peer`、`teasing`、`conflict`、`avoidance`、`custom`，不再回退显示英文。

未来画像卡片只新增 presenter；本阶段保留结构化快照、事实、经历、关系和管理员治理 API，不实现卡片版式，也不开放成员编辑。

## 验收标准

1. 相同 observed pattern 分散在三个批次后成为一条 confirmed fact。
2. 相同成员关系分散在三个批次后成为一条 confirmed edge。
3. 第三方说法与本人自述内容相同也不会合并。
4. 每批处理后整群画像的成员数、活跃节奏、角色和关系计数更新。
5. 后台未预期异常不会终止任务，健康接口能看到安全诊断和时间。
6. 外部命令不入画像队列，普通闲聊仍会入队。
7. 管理页不显示错误成熟度或未翻译的关系枚举。
8. 成员侧仍只有 `查看我的画像`。
