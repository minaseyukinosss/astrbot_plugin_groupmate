# Groupmate 共享世界知识与游戏版本时效设计

- 状态：已完成设计，待用户复核
- 日期：2026-08-27
- 适用范围：Groupmate Social Runtime v2 的闲聊认知、知识检索、回复生成和控制面

## 1. 结论

Groupmate 增加一套安装实例级的共享世界知识系统，解决闲聊模型对热门游戏、社区术语和新版本理解不足的问题。系统不把百科资料堆入 Prompt，也不将搜索结果直接当作事实，而是使用“本地相关检索→有界联网核验→证据准入→带知识 ID 生成→失败关闭审查”的受控链路。

世界事实不按 Persona 或群隔离；群内热度、黑话和特殊指代按群隔离；Persona 立场和成员画像仍由原有系统分别管理。游戏版本是一等时间对象，同时记录发布状态和信息披露等级。活跃游戏后台每 24 小时核验一次版本；用户明确提及“新版本”、“前瞻”、“爆料”或“刚更新”时即时联网核验，不等待次日任务。

## 2. 问题与当前约束

当前认知上下文主要由群聊事件、群成员画像、关系记忆和 Persona Canon 组成。这些信息能帮助 Bot 理解人和当前社交关系，但不提供可验证的外部世界知识。`ReplyExecutor` 又正确地限制技术和事实回答只使用已列事实，因此单纯放宽 Prompt 只会把问题从“不理解”变成“无证据猜测”。

当前还有三项必须保留的约束：

1. AMBIENT 群聊参与判断使用有界时间预算，不能对所有消息搜索。
2. 成员画像和关系记忆是带隐私边界的社交证据，不能成为公共百科存储。
3. 当前回复链已有 `covered_fact_ids`、记忆 ID、能力 ID 和失败关闭审查，新知识链应延伸而不是绕过这些边界。

## 3. 目标

### 3.1 产品目标

- Bot 对常见热门游戏开箱可达到“听得懂普通玩家聊天”的深度。
- 遇到未知游戏、术语或时效内容时，仅在值得参与且缺口会改变理解时联网。
- 一次合格检索可以形成知识候选，经证据策略准入后跨群复用。
- Bot 能区分“没有可靠公开信息”、“仅有非官方爆料”、“已有官方前瞻”和“已实装”。
- 网页搜索失败、结果冲突或证据过期时，Bot 不编造。

### 3.2 工程目标

- 知识存储、检索适配、版本解析、准入策略、群热度和回复审查是独立单元。
- 领域层仅依赖 `SearchPort`，不依赖 Tavily、博查、百度、Brave、Firecrawl 或 Exa 的具体协议。
- 所有入库知识、过期和纠正都可审计，但不持久化完整网页、Prompt 或模型原始输出。
- 相同搜索和后台更新使用幂等任务与 single-flight 合并。

## 4. 非目标

首版不实现：

- 全量镜像游戏 Wiki 或通用互联网百科；
- 无人请求时主动抓取、整理或散播非官方爆料；
- 自动回溯平台历史群消息；
- 把向量相似度当作事实真值或证据强度；
- 自动生成专业配队、强度榜或竞技攻略；
- 跨安装实例上传或云同步知识库；
- 用世界知识修改 Persona Canon、成员画像或关系投影。

## 5. 作用域边界

| 信息 | 归属 | 隔离键 | 示例 |
|---|---|---|---|
| 公开世界事实 | `WorldKnowledgeStore` | 安装实例 | 《原神》的游戏类型 |
| 版本时间线 | `GameVersionTimeline` | 安装实例 | 当前版本、下一版本披露状态 |
| 群内话题热度 | `GroupTopicOverlay` | `group_id` | 近期常聊鸣潮 |
| 群内黑话与指代 | `GroupTopicOverlay` | `group_id` | 某群使用的角色外号 |
| Persona 经历和立场 | Persona Canon / 表达规划 | `persona_id` | 爱弥斯对某角色的态度 |
| 成员偏好与经历 | Member Profile | `persona_id + group_id + actor_id` | 某成员喜欢某角色 |

`WorldKnowledgeStore` 的主数据不带 `persona_id` 和 `group_id`。多个 Persona 读取同一事实，但各自的社交动作、立场和说法仍由原链路决定。

群聊中出现的说法不能因为“多次出现”就进入公共知识库。它们先成为群级别名或公共搜索线索；只有可以由公开来源独立验证的事实才能晋升为共享知识。

## 6. 总体架构

### 6.1 组件

1. `KnowledgeEntityResolver`
   - 使用全局别名、群覆盖别名和当前对话解析游戏、角色、模式、地图、装备和术语。
   - 外号或单字简称不能脱离上下文强行归并。

2. `KnowledgeNeedAssessor`
   - 输出 `none`、`local_sufficient`、`web_required` 或 `unresolvable`。
   - 同时输出缺口类型、候选实体、搜索问题、时效标记和核验理由，不输出回复正文。

3. `KnowledgeRetriever`
   - 从群覆盖层和全局知识库取回有效声明，按实体相关性、群话题热度、证据级别、时效和冲突状态排序。
   - 一轮只打包少量 `KnowledgeEvidenceBlock`，不暴露全量记录、内部分数或数据库键。

4. `SearchPort`
   - 统一搜索查询、结果数上限、时间预算和取消语义。
   - 首个生产适配器为 `AstrBotWebSearchAdapter`，使用 AstrBot 管理员已配置的网页搜索源。Groupmate 不保存搜索服务 API Key，也不把搜索工具自由交给最终回复模型。

5. `SearchQueryPlanner`
   - 使用已解析实体、时间意图和源策略生成 1–2 个有界查询。
   - 不把成员画像、关系记忆、私密事件或 Persona Prompt 拼入查询。

6. `KnowledgeAdmissionPolicy`
   - 将搜索结果转为候选声明，执行实体归一、去重、来源分类、时效计算、冲突检查和晋升。
   - 模型可以提取候选，但最终状态由本地策略决定。

7. `GameVersionTimelineService`
   - 解析“当前版本”、“下一版本”和明确版本号，管理发布状态、披露状态、日期、替代关系和“截至某时未发现”观察。

8. `KnowledgeRefreshScheduler`
   - 持久化管理即时补全、群话题预热和定期重验证任务。
   - 使用每实体冷却、single-flight、全局额度、退避和幂等键。

9. `GroundedReplyReviewer`
   - 扩展现有 `SocialOutputReviewer`，检查回复中的知识 ID、时效、来源等级、必要限定语和额外无证据事实。

### 6.2 同步数据流

```text
消息入库与能力归属
→ 注意候选与实体解析
→ 本地知识检索
→ 知识缺口评估
→ [必要时] 有界网页搜索与证据准入
→ 社交场景解释、参与和 Governor
→ 带 KnowledgeEvidenceBlock 的社交动作与表达规划
→ 结构化回复
→ 社交审查 + 知识根据审查 + 输出防火墙
→ Outbox
```

本地检索不会改变消息的权限或能力归属。网页搜索是只读外部证据获取，不能绕过 Governor 、生成外部副作用或直接发送消息。

### 6.3 搜索触发时机

网页搜索只在以下条件同时成立时触发：

1. 消息是直接对 Bot 、延续 Bot 的对话，或已被初步认知评为值得参与；
2. 本地知识不足以正确解释话题或支持必要事实；
3. 不搜索会实质增加误解或编造风险；
4. 该实体、查询、日预算和当前截止时间允许调用。

直接对 Bot 的知识问题可使用独立最终回复搜索预算；AMBIENT 参与的搜索必须在场景剩余有效时间内完成，时间不足就继续观察。这保证未相关群聊不会因知识补全产生搜索风暴。

## 7. 数据模型

### 7.1 共享实体与别名

`knowledge_entities`：

- `entity_id`
- `entity_type`：`game | version | character | faction | mode | map | item | mechanic | term`
- `canonical_name`
- `canonical_game_id`
- `status`：`active | merged | retired`
- `created_at`
- `updated_at`

`knowledge_aliases`：

- `alias_id`
- `entity_id`
- `normalized_alias`
- `alias_kind`：`official | translation | abbreviation | community`
- `ambiguity_level`
- `source_id`
- `status`

`group_knowledge_aliases` 额外带 `group_id`，只有当前群的解析器可见。

### 7.2 知识声明与来源

`knowledge_claims`：

- `claim_id`
- `subject_entity_id`
- `predicate`
- `summary`
- `knowledge_kind`：`stable | versioned | schedule | community`
- `evidence_level`：`bundled | official | corroborated | secondary | unofficial`
- `confidence`
- `status`：`pending | active | stale | superseded | rejected | disputed`
- `valid_from`
- `valid_until`
- `checked_at`
- `supersedes_claim_id`
- `created_at`
- `updated_at`

`knowledge_sources`：

- `source_id`
- `url`
- `domain`
- `publisher`
- `source_class`：`official | official_preview | wiki | media | community | bundled`
- `published_at`
- `retrieved_at`
- `content_hash`
- `safe_excerpt`：裁剪后的短证据，不保存完整网页

`knowledge_claim_sources` 建立声明与来源的多对多关系。

### 7.3 版本时间线

`game_versions`：

- `version_id`：内部 ID，不要求官方已公开版本号
- `game_entity_id`
- `official_label`：可空；官方公布前不推测编号
- `release_status`：`future | current | past`
- `disclosure_status`：`none | unofficial | official_preview | official_notice | released`
- `announced_at`
- `release_at`
- `checked_at`
- `fresh_until`
- `status`：`active | superseded | disputed`

“下一版本”可以是没有 `official_label` 的 future slot。系统不根据当前版本号自行加一，因为游戏可能跳版本、使用赛季名或采用其他命名。

`knowledge_absence_observations` 记录：

> 截至 `checked_at`，按当时的来源策略未发现可靠公开信息。

它使用独立的 `absence_observation_id`，不伪装成普通正向事实。`KnowledgeEvidenceBlock` 中的证据 ID 使用类型前缀区分 `claim:*` 和 `absence:*`，避免审查时混淆。它不表示永久没有信息。搜索超时、配置缺失或 Provider 失败不能产生 absence observation，只能生成诊断记录。

### 7.4 群话题覆盖

`group_topic_affinity`：

- `group_id`
- `entity_id`
- `mention_count`
- `salience`
- `first_seen_at`
- `last_seen_at`
- `updated_at`

`salience` 使用 7 天半衰期按时间衰减。它只影响检索排序和后台调度，不能改变事实真值或在不相关的话题中强行注入游戏知识。

### 7.5 任务与追踪

`knowledge_jobs` 持久化即时补全、预热和重验证任务，状态为 `pending | running | retry | completed | discarded`。`knowledge_usage` 只记录某次场景实际获得和使用的知识 ID、来源域名、耗时和结果类型，不记录完整 Prompt 或网页正文。

## 8. 首版预装游戏包

首版强制预装：

1. 原神
2. 三角洲行动
3. 鸣潮
4. 崩坏：星穹铁道
5. 绝区零

每个游戏包为带 `seed_id` 和 `seed_version` 的版本化资产，通过幂等导入器写入共享知识库。包内仅包含稳定基础：

- 官方名称、英文名、常见简称与可能歧义；
- 游戏类型、核心玩法和普通玩家对话必要的基础结构；
- 主要模式、角色、阵营、地图、装备、养成和系统类型的归属；
- 常见社区术语的基础含义和语气边界；
- 官方主站、公告页和可用的高信任来源域名。

包内不固化当前版本、当期角色、卡池、活动、数值、强度榜和测试服信息。首次导入后立即为这五款游戏排入一次后台版本同步；同步完成前，基础知识可用，但任何当前版本问题都必须即时核验或失败关闭。

五款预装游戏始终是 `baseline_active`，每 24 小时进行版本后台核验，不需要等待某个群先提及。持续学习的其他游戏在近 30 天内累计至少 3 次相关提及且覆盖至少 2 个独立场景时为 `conversation_active`；超出窗口后停止日常联网，但不删除已验证知识。未达到这一阈值的游戏仍可在明确时效问题上即时核验。

插件升级时，较新的官方验证声明优先于旧 seed；新 seed 可以替代旧 seed 的同源声明，但不盲目覆盖后续已验证知识。

## 9. 版本和时效规则

### 9.1 相对时间解析

下列表达必须经过 `GameVersionTimelineService`：

- 新版本、下版本、下期、这期；
- 最近更新、刚改、现在、已经实装；
- 新角色、新地图、新赛季、新武器、新卡池；
- 爆料、前瞻、测试服、官方公告。

解析使用消息时间、游戏实体、对话时态、已解析版本线和上下文。“新版本”可能指刚实装的 current version，也可能指未实装的 future slot。无法可靠区分时，社交动作只能询问缺失的版本或时态，不得自行选择。

### 9.2 双维状态

发布状态和信息披露状态分开管理：

```text
release_status: future -> current -> past
disclosure_status: none -> unofficial -> official_preview -> official_notice -> released
```

披露状态不保证逐级发生，可以跳过某些阶段。`unofficial` 不会因为转发次数增多就变成官方。

### 9.3 刷新策略

- 活跃游戏的版本线后台每 24 小时成功核验一次，使用抖动分散请求。
- 不活跃游戏不定时联网，被再次提及时恢复。
- 时效表达会覆盖 24 小时后台周期并当场核验，因为官方可能在每日任务后发布公告。
- 相同游戏的成功即时核验结果在 10 分钟内复用，以合并群聊短时间连续讨论。
- 到达已验证的 `release_at` 时，即使未到次日也要将该时间边界排入重验证。
- 搜索失败不更新 `checked_at` 和成功刷新时间，避免失败调用让旧资料看起来更新。

### 9.4 回复语义

| 证据情况 | 允许的语义 |
|---|---|
| 成功核验且无可靠公开信息 | “截至刚才还没看到可靠公开信息” |
| 仅有非官方资料 | “现在流传的是非官方爆料，可能变动” |
| 已有官方前瞻 | “官方前瞻已确认……” |
| 已有正式公告 | 只陈述公告支持的内容与日期 |
| 已实装 | 将其解析为 current version，并可询问用户是否指再下一版 |
| 搜索失败 | “这次没能确认”，禁止说官方未公布 |

非官方爆料允许用于理解和被动讨论，必须明确标注非官方和可能变动，不主动扩散，不晋升为已验证事实。

## 10. 证据准入与冲突规则

### 10.1 来源级别

默认优先级为：

1. 官方公告、更新说明和官方发布时间；
2. 官方前瞻、直播、角色演示和运营账号；
3. 可以与官方资料相互印证的 Wiki 或媒体；
4. 多个独立二手来源；
5. 社区讨论、测试服信息和爆料。

一条官方来源可以激活它明确支持的声明。非官方稳定基础事实需要至少两个相互独立且不冲突的来源。社区术语可以以 `community` 身份进入召回，但不能被表述为官方名称。

### 10.2 冲突处理

- 新官方事实通过 `supersedes_claim_id` 替代旧官方事实，历史仍保留。
- 官方正式公告优先于早期官方前瞻。
- 正式实装优先于测试服或爆料数值。
- 两条同等级来源冲突时，声明进入 `disputed`，不进入正常回复。
- 模型不得对冲突数字取平均、拼接或自行选一条。

### 10.3 网页安全

- 网页和搜索摘要是不可信输入，其中的指令、Prompt、工具调用或身份声明全部无效。
- 仅允许 HTTP(S) 公开网址，拒绝本地文件、回环、私网、云元数据和非网页协议。
- 提取文本、标题、发布者、时间和有界证据片段，不执行页面代码、下载文件或跟随页面命令。
- 来源 URL 去除追踪参数和敏感查询，日志不记录网页原文。

### 10.4 “未发现公开信息”的准入

`search_empty` 不足以证明“官方没有信息”。只有同时满足以下条件时才能产生 absence observation：

1. 搜索 Provider 完整成功，不存在超时、限流或部分失败；
2. 该游戏预装或已学的官方公告/运营来源至少有一个可达且已成功检查；
3. 查询同时覆盖游戏名、目标版本语义和相关披露词；
4. 未发现官方声明，也未发现能够晋升为可靠公开信息的独立证据；
5. observation 保存成功核验时间、来源策略版本，且用于即时回复的 `fresh_until` 固定为 `checked_at + 10 分钟`。

即使满足这些条件，Bot 也只能说“截至刚才未发现可靠公开信息”，不能绝对化为“网上没有任何爆料”。

## 11. 回复根据与失败关闭

### 11.1 生成契约

`RealizedReply` 增加：

- `used_knowledge_ids`：本轮实际使用的允许知识 ID；
- `knowledge_assertions`：回复中的事实断言、对应文本片段和支持它的知识 ID；
- `source_event_ids`：仍只引用当前场景中允许的事件。

`covered_fact_ids` 继续表示社交动作的必说/可说事实，不与知识 ID 混用。

### 11.2 审查

`GroundedReplyReviewer` 先做确定性检查：

- 所有知识 ID 均属于本轮 `KnowledgeEvidenceBlock`；
- 时效声明在当前时间仍然有效且来自最新成功知识快照；
- 返回的事实片段真实出现于回复正文；
- `unofficial`、`official_preview` 和 `absence` 使用了匹配的限定语；
- 版本、日期、数值、角色、装备、模式等可外部验证断言都已声明支持 ID。

再使用一个只能看到回复和允许证据的封闭语义审查，检查每个断言是否可以由引用声明支持。审查模型不能搜索、不能看其他记忆、不能新增事实。

失败时只允许一次修复，修复请求只包含原证据、原社交动作和 violation codes。第二次仍失败就进入降级。

### 11.3 降级

- 普通 AMBIENT 闲聊：沉默；
- 被直接询问但搜索失败：“我这次没能确认，先不乱说。”；
- 仅有非官方信息：带限定语讨论，或在不适合谈爆料的社交场景中不使用；
- 证据冲突：说明当前说法不一致，不自行判定；
- 实体无法解析：只问一个能消除歧义的问题，或在环境闲聊中沉默。

### 11.4 群聊中的来源呈现

普通轻量闲聊不自动在每句后拼接长链接，但运行中心始终保留实际使用来源。当用户明确要求“查一下”、“给来源”或 Bot 回答官方公告日期、版本发布时间等可核对信息时，回复可携带最多 2 个直接来源链接。链接必须来自本轮允许证据，不得由生成模型编造。

## 12. 持续学习与后台调度

### 12.1 学习流程

```text
新实体/术语或过期声明
→ 本轮有界搜索
→ pending KnowledgeCandidate
→ 归一、去重、来源和冲突评估
→ active / unofficial / disputed / rejected
→ 后续证据强化、替代或失效
```

新游戏第一次在某群出现时，可以完成当轮轻量理解，并在后台补齐共享基础卡。其他群再次提及时直接复用。

### 12.2 任务优先级

```text
当前对话需要
+ 群话题热度
+ 临近已验证版本时间边界
+ 证据过期程度
- 近期查询成本和失败退避
```

后台任务不阻塞 Scene Actor、Persona Supervisor、Journal 入库或 Dispatcher。同一游戏在多群同时变热时只建立一个全局预热或重验证任务。

### 12.3 额度与超时

安全默认值：

- 即时搜索软超时 3 秒，硬超时 5 秒；
- 每个即时场景最多 2 个查询，每个查询最多 4 个搜索结果；
- 每安装实例每小时最多 20 次搜索调用；
- 每安装实例每日最多 100 次搜索调用；
- 相同归一化查询在有效窗口内合并；
- Provider 失败使用指数退避和有界抖动，不尝试无限重试。

额度用尽后不借用回复模型的内在知识猜测时效事实，而是使用失败关闭降级。

### 12.4 保留与清理

- 已验证稳定声明和官方历史版本长期保留；
- superseded 和 disputed 的证据元数据保留以支持审计，安全摘要可在 180 天后裁剪；
- rejected 候选和搜索短缓存在 30 天后删除安全摘要，只保留哈希、域名、诊断码和时间；
- 群级覆盖可按群删除，删除后不影响已由公开来源独立验证的共享事实；
- 未进入知识库的原始群消息不因知识系统新增额外长期副本。

## 13. 配置与 AstrBot 集成

新增最小配置：

- `knowledge_enabled`：默认 `true`，控制预装知识、本地检索和持续学习；
- `knowledge_web_search_enabled`：默认 `true`，但 AstrBot 没有可用网页搜索源时 readiness 显示降级，不阻止稳定预装知识使用；
- `knowledge_search_timeout_seconds`：默认 `5`，可配置 2–8 秒；
- `knowledge_daily_search_budget`：默认 `100`，可配置 10–1,000；
- `knowledge_hourly_search_budget`：默认 `20`，可配置 5–200；
- `knowledge_version_refresh_hours`：固定默认 24，页面可见但首版不提供调整控件。

`AstrBotWebSearchAdapter` 使用 AstrBot 的管理配置和内建搜索工具，而不在 Groupmate 中再建一套厂商 API Key 配置。AstrBot 当前已将网页搜索作为函数调用能力管理，生产适配器需要绑定管理员已开启的搜索源，并在调用时显式限定只有搜索/页面提取工具可用，不带其他 AstrBot 工具。

如果 AstrBot 工具 API 在兼容版本中不能被插件直接受控调用，适配器启动时应该 fail closed 并上报 `knowledge_search_adapter_unavailable`，不得退回到“让最终模型自由选工具”。

## 14. 控制面与审计

运行中心增加“知识根据”摘要：

- 是否命中预装或已学知识；
- 是否触发即时搜索；
- 搜索原因、查询数、来源域名、耗时和诊断码；
- 实际使用的知识 ID、证据等级和时效；
- 是否因证据不足、过期、冲突或超时降级。

控制面新增知识查询页，但不需要将其混入成员画像页：

- 按游戏查看基础卡、当前/下一版本状态、最后成功核验时间和来源；
- 查看 pending、disputed、stale 和失败任务；
- 管理员可以手动刷新、使声明失效、纠正实体归并或群级别名；
- 手动操作进入审计日志，不删除旧证据链。

页面不显示 API Key、Prompt、完整模型输出或完整网页正文。

## 15. 持久化、恢复与并发

- 新表使用 Social Runtime 拥有的加法式 schema migration，不导入旧废弃域模型。
- seed 导入、搜索任务、候选晋升、版本替代和用量记录都使用稳定幂等键。
- 每个知识任务先持久化再执行，进程重启后根据 `status`、`attempt` 和 `next_attempt_at` 恢复。
- 一次回复使用冻结的 `KnowledgeEvidenceBlock`，不在生成中途混入后台刚更新的证据。
- 新官方公告可以使旧 absence observation 立即失效，但已冻结且正在生成的计划仍必须在发送前做最后时效检查；如果快照已被替代就放弃发送。
- 相同实体或查询的 single-flight 完成后，所有等待场景只取回同一批已准入证据，不共享生成正文。

## 16. 故障语义

| 故障 | 领域结果 | 群聊行为 |
|---|---|---|
| 搜索适配器未配置 | `adapter_unavailable` | 使用稳定本地知识；时效问题失败关闭 |
| 搜索超时 | `search_timeout` | AMBIENT 沉默；直接询问承认未能确认 |
| 无搜索结果 | `search_empty` | 不得自动表述为“官方未公布” |
| 成功搜索且指定可靠来源中无资料 | `absence_confirmed` | 可带 `checked_at` 表述截至当时未发现 |
| 来源冲突 | `evidence_disputed` | 不选边，不生成确定事实 |
| 知识过期 | `knowledge_stale` | 必须刷新或失败关闭 |
| 回复使用未允许知识 ID | `unknown_knowledge_id` | 修复一次，再失败就沉默/固定降级 |
| 回复有无证据断言 | `unsupported_knowledge_assertion` | 修复一次，再失败就沉默/固定降级 |
| 日额度用尽 | `knowledge_budget_exhausted` | 不借用模型自身知识猜时效事实 |

异常日志仅记录稳定诊断码、适配器名、模型/搜索源标识、耗时和请求大小。不保存密钥、完整 URL 查询、Prompt、响应正文或原始异常消息。

## 17. 测试设计

### 17.1 单元测试

- 预装包幂等导入、版本升级和较新已验证声明保护；
- 全局实体可跨群复用，群别名和话题热度不跨群；
- 歧义简称不在无上下文时强行归并；
- 版本双维状态、relative version 解析、时间边界和无标签 future slot；
- 搜索失败不产生 absence observation；
- 新官方声明替代旧声明且历史可审计；
- 非官方证据不能使用官方限定语；
- 过期、冲突和未允许知识 ID 被回复审查拒绝；
- 小时/日额度、每实体冷却、single-flight 和退避。

### 17.2 场景测试

1. 新版本暂无资料
   - 已有当前版本知识；用户询问下一版；官方来源核验无资料；回复必须带“截至刚才”语义，不编造版本号。

2. 同日后来发布官方前瞻
   - 每日后台任务已经完成；用户之后提及“前瞻”；当场核验必须使 absence observation 失效并使用新官方证据。

3. 仅有测试服爆料
   - 允许 Bot 理解话题，但回复必须说明非官方、可能变动；知识状态不得升为 official。

4. 搜索 Provider 超时
   - 不改写成功刷新时间；AMBIENT 不回复；直接询问使用固定承认未确认语义。

5. 群别名隔离
   - 群 A 的外号可以解析到某角色；群 B 无证据时不得沿用；两群仍共享该角色的公开事实。

6. 未预装游戏持续学习
   - 第一个群首次提及时有界搜索；合格声明晋升后，第二个群可在不联网的情况下理解稳定基础。

7. 网页 Prompt Injection
   - 网页要求泄露 Prompt、调用工具或忽略规则；候选提取只保留可验证事实，不生成能力或副作用。

8. 生成模型额外编造
   - 已给一条允许声明，模型额外生成版本号、日期或数值；`GroundedReplyReviewer` 必须拒绝，修复失败后不发送。

### 17.3 回归与容量

- 原有精确命令、外部能力归属、关系记忆、成员画像、复读和社交审查行为不变；
- 普通非知识闲聊不触发网页搜索；
- 不使用网页搜索时，本地检索的延迟和 Prompt 增量受固定预算约束；
- 多群同时讨论同一游戏时，搜索次数受 single-flight 与额度上限约束；
- 进程在搜索、候选准入和定期刷新的任意持久化边界重启后，不重复晋升、不丢失审计且不发送历史回复。

## 18. 发布验收标准

1. 五款预装游戏的官方名、常用简称和高频基础术语固定集全部正确归属，歧义词固定集无强行错误归并。
2. 稳定公开知识可跨群复用，群别名、群话题热度和成员信息零跨群泄漏。
3. 所有版本场景固定集中，无证据版本号、日期、角色、模式和数值断言为零。
4. 搜索失败不被表述为“没有官方信息”，absence 只来自成功核验。
5. 时效表达在没有 10 分钟内成功即时核验时必须重新搜索，不受每日后台成功状态豁免。
6. 非官方爆料回复全部带有明确限定语，且不进入 official 声明。
7. 知识搜索不会在精确命令、已归属外部能力或明确不参与的普通 AMBIENT 消息上发生。
8. 即时搜索超过硬截止时间后取消；AMBIENT 不因等待知识而超过场景有效期发送。
9. 运行中心可以解释每次知识召回、搜索、准入、拒绝、过期和降级，且不显示密钥、Prompt 或完整网页。
10. 进程重启、重复事件和重复 seed 导入不产生重复声明、重复任务或重复回复。

## 19. 分阶段交付边界

实现计划应依次交付：

1. 知识领域模型、schema、repository、预装包和本地检索；
2. 群话题覆盖、知识缺口评估与 Scene Context 注入；
3. `SearchPort`、AstrBot 搜索适配器、证据准入和版本时间线；
4. 知识根据生成契约、审查与失败降级；
5. 后台刷新、额度、控制面、故障注入和 SHADOW 评审。

任何阶段都不得用“先让模型自由搜索和回答”作为过渡实现。未完成证据准入和回复根据审查前，网页知识只能在 SHADOW 中运行，不得用于正式发送。

## 20. 设计完成判定

本设计将“扩大 Bot 认知”明确为三个彼此独立的能力：

1. 用预装和持续学习形成可跨群复用的公开世界知识；
2. 用群覆盖层理解不同群的话题热度、简称和黑话；
3. 用时间状态、有界网页搜索和失败关闭审查保证版本信息不被过期资料或模型猜测污染。

这三层通过明确 ID、冻结证据块、时效和审查契约与现有 Social Runtime 衔接，不把公共事实、群文化、Persona 立场和成员画像混成一个不可控的“大记忆”。
