# 运行状态、消息终态与人格配置收敛设计

日期：2026-08-26  
范围：Groupmate 运行中心、消息链路查询、AstrBot 原生插件配置

## 1. 目标

本轮解决三个直接影响管理员判断的问题：

1. 普通群聊消息不再长期停留在“等待处理”；
2. 运行中心显示当前群真正生效的运行状态，而不是静态或过期配置；
3. 消息数量不再把最近 200 条误写成累计总数，并能继续加载更早记录；
4. 人格配置只表达“她是谁、群友怎样称呼她”，不再暴露无法理解和检查的双层 Persona 配置。

本轮不调整参与策略、模型提示词、好感度算法、群友画像提取规则或 AstrBot 外部插件能力。

## 2. 已确认的根因

### 2.1 普通群聊批次只关闭了一条 Trace

普通消息会进入 2–5 秒的 AMBIENT 注意窗口。一个窗口最多携带多条 `focus_event_ids`，但 `MessageTraceRepository.record_evaluation()` 目前只更新 `evaluation.source_event.event_id`。同一窗口的其他消息已经参与了理解，却仍保留 `PENDING`，造成长期“等待处理”。

### 2.2 看板没有运行实例这一事实来源

控制 API 在初始化时复制 `settings.runtime_mode`，Bootstrap 后持续返回这个静态值。页面又无条件优先采用 `configured_runtime_mode`，因此看不到当前群的 Manager 是否已启动、实际运行于 SHADOW 还是 SOCIAL_RUNTIME，也不能表达“配置值与实际值不一致”。

### 2.3 200 是查询窗口而不是接收上限

Trace 查询包含固定 `LIMIT 200`。数据库继续保存更多消息，但 API 没有返回总数、游标或下一页，页面的“加载更多”只能展开已下载的 200 条。运行概览又直接使用 `items.length` 作为“已收到”，所以该数字会停在 200。

### 2.4 人格身份存在三个互相遮蔽的入口

- `persona_name` 是正式名称，也参与直接呼唤识别；
- `persona_aliases` 是其他可接受称呼；
- `persona_preset` 提供剧情事实和表达禁区，但身份名称又会被前两项覆盖；
- `custom` 选项没有完整可视化编辑与检查入口。

这让管理员无法判断最终生效的人格来自哪里。

## 3. 消息终态设计

### 3.1 AMBIENT 窗口的主消息

`evaluation.source_event` 保持现有完整展示：模型理解、参与判断、决策原因、候选回复和交付状态均记录在该消息行。

### 3.2 同窗口的上下文消息

对 `frame.focus_event_ids` 中除主消息外、且仍处于非终态的 Trace，写入以下终态：

- 理解：`READY`，文案“已纳入同一轮群聊理解”；
- 判断：`OBSERVE`，`would_reply=false`，文案“作为上下文参与判断”；
- 最终结果：`OBSERVED`，文案“已纳入群聊上下文”；
- 阶段：补齐 ATTENDED、UNDERSTOOD、DECIDED。

已进入 `SENT`、`SILENT`、`OBSERVED`、`BLOCKED_BY_SHADOW`、`HANDED_OFF`、`FAILED` 或 `UNKNOWN` 的 Trace 不得被上下文终态覆盖。这样可以处理并发的 FAST/CONTINUATION 判断而不降级已有结果。

### 3.3 正常等待文案

真正处于注意窗口中的短暂状态不再显示模糊的“等待处理”，而显示“正在等待本轮群聊收束”，详情说明“普通群聊通常会合并 2–5 秒上下文后判断”。

## 4. 实时运行状态设计

### 4.1 单一事实接口

Bridge 新增按群读取的只读运行状态：

```json
{
  "configured_mode": "SOCIAL_RUNTIME",
  "effective_mode": "SOCIAL_RUNTIME",
  "state": "RUNNING",
  "ready": true,
  "blockers": []
}
```

`effective_mode` 必须在请求发生时由当前 Manager 的 `group_mode(group_id)` 计算，不能从历史投影或页面缓存推断。Manager 不存在、尚未启动或启动失败时，`state` 分别返回 `STOPPED`、`STARTING` 或 `FAILED`，并给出经过裁剪的管理员可见原因。

### 4.2 控制 API 与看板

Bootstrap 同时返回配置值和实际值：

- `configured_runtime_mode`：AstrBot 原生配置希望采用的模式；
- `effective_runtime_mode`：当前群实际生效模式；
- `runtime_state`：实例生命周期状态；
- `runtime_ready` 与 `runtime_blockers`：当前是否可以处理消息及原因。

运行中心主标题只使用实际状态。配置值与实际值不一致时，显示“配置已修改，但运行实例尚未应用；请重载插件”，不能把配置值冒充运行事实。

## 5. Trace 总数与分页

### 5.1 查询契约

`GET traces` 支持：

- `limit`：默认 100，最小 1，最大 200；
- `before`：上一页返回的不可解释游标；
- 返回 `total_count`、`items`、`next_cursor`、`has_more`。

游标基于 `(received_at, entity_ref)`，查询始终限定在同一 Persona 和群。游标只作为翻页令牌，不进入页面搜索文案或日志。

### 5.2 页面行为

- 运行概览显示数据库累计 `total_count`；
- 消息区显示“已加载 Y / 共 X 条”；
- “加载更多”向服务端请求下一页并合并，不再只是展开本地数组；
- 立即刷新只刷新第一页和总数，旧页继续保留，除非切换群或筛选作用域；
- 搜索仍只搜索已加载内容，并明确显示“搜索已加载记录”，避免声称全库搜索。

本轮不引入自动清理或数据保留期限；数据库接收数量不设 200 条上限。

## 6. 人格配置收敛

### 6.1 AstrBot 原生配置可见字段

可见字段改为：

- `运行方式`：SHADOW 观察 / 正式运行；
- `正式名称`：默认“爱弥斯”，说明“她的自称，也是群友可以直接呼唤的名称”；
- `其他称呼`：默认包含“小爱”，说明“每行一个，不要重复正式名称”。

不再显示 `人格资料预设`。当前发行版的新配置固定使用 `aemeath_current`，插件页面明确显示“当前人格：爱弥斯（当前剧情）”。

### 6.2 兼容规则

- 解析器继续读取旧配置中的 `persona_preset` 和 `custom`，避免升级时破坏已有实例；
- 新版 `_conf_schema.json` 不再提供新建 `custom` 的入口；
- 已保存的正式名称和其他称呼继续保留；只有字段缺失时才使用“爱弥斯”和“小爱”默认值；
- 同正式名称重复的别称继续去重，但配置说明提前阻止这种误填；
- 已发布的群级 Persona Profile 仍为该群的最终身份来源，运行中心显示解析后的最终名称，而不是原始配置字段。

## 7. 页面文案

运行状态只允许使用以下主状态：

- “爱弥斯正在运行”
- “爱弥斯正在 SHADOW 观察”
- “爱弥斯尚未就绪”
- “爱弥斯已停止”
- “配置尚未应用”

数量文案使用：

- “累计收到 X”
- “进入 Groupmate Y”
- “准备回复 Z”
- “成功发送 N”
- “认知异常 M”

页面不再以“Groupmate 当前未运行”描述一个已启动的爱弥斯实例。

## 8. 测试与验收

按测试优先实现以下最小覆盖：

1. 两条普通消息合并为一个 AMBIENT 窗口后，两条 Trace 均进入终态；
2. 已有终态不会被上下文终态覆盖；
3. Bootstrap 返回当前群的实际模式，并能表示配置不一致；
4. Trace 超过 200 条时，总数正确且第二页可读取；
5. 页面“加载更多”会发起服务端查询，累计数不再等于当前数组长度；
6. 新配置默认正式名称“爱弥斯”、其他称呼“小爱”，且不再显示 Persona 预设选择器；
7. 旧 `custom`、旧名称和旧别称仍可被解析。

只运行与 Trace、控制 API、运行中心和设置 Schema 直接相关的定向测试，再做一次 `git diff --check`；不执行无关的大型测试套件。

验收标准：

- 运行 15 秒后，已进入 Groupmate 的普通消息不存在无原因的永久 `PENDING`；
- 看板主状态与当前群的 Manager 模式一致；
- 第 201 条及更早消息可以通过“加载更多”读取；
- 管理员无需理解 Persona Profile、Preset 和 Alias 的内部层级即可完成爱弥斯身份配置。
